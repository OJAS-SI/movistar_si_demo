## 1. Bilingual EN/ES

The console is bilingual end to end. Toggle is in the header beside the scale selector;
the choice persists to `localStorage`.

**Architecture** (chosen deliberately, and it is the thing to preserve):

- `si_core` emits `Msg(key, params)` — a key and its facts, **never a finished
  sentence**. The domain never imports a language.
- `si_core/messages.py` holds the **canonical English** catalogue and renders its own
  English, so `run_demo.py`, the text console and the HTML export still work with no API
  present.
- `si_api/i18n.py` holds **Spanish** and picks per request: `?lang=` wins, else
  `Accept-Language`, else English.
- Frontend chrome is a separate dictionary, `frontend/src/lib/i18n.ts` (155 keys, zero
  unused, all with Spanish).

**Switching language re-reads the same run. It never re-runs the engine** — verdicts and
every number are identical, only prose is re-rendered.

**Verified**: on a live run, EN vs ES have **0 non-prose differences** — every number,
id, layer, shape and `action_code` byte-identical.

### A live bug this closed
`scoring.py` proved box-swap discrimination with `"box" in action.lower()`. The moment
the recommendation became Spanish that check would have passed on **every** input while
measuring nothing — a *false pass* on the demo's headline claim. Scoring now reads
`ActionCode`, pinned by `test_module9_messages.py`.

### Duplication collapsed
English used to be hand-written twice (f-strings in the domain, and again as display
text). `si_core` now renders its English from the catalogue, so the web and text consoles
cannot drift. That collapse also fixed a latent English bug: *"1 homes elevated"* →
*"1 home elevated"*.

### Terminology decision
Equipment and protocol names stay as an operations team writes them — OLT, STB, FEC,
SNR, WAN, CDN, set-top box, gateway, encoder, core. Only the prose around them is
Spanish. Translating the acronyms would read as unnatural to engineers and would break
the correspondence with the entity ids on the same screen.

## 2. Seamless tiny ⇄ full toggle

| action | before | after |
|--------|--------|-------|
| select **full** | ~84 s | **1 ms** |
| stream 576 full frames | ~84 s | **0.04 s** |
| select **tiny** | 0.2 s | **1 ms** |

Three separate causes, only the third obvious:

1. `RunStore.create()` always minted a new `run_id`, so full → tiny → full recomputed
   every time, despite a run being fully determined by `(scale, seed)`.
2. **`stream.py` never reused a finished run** — it called `replay(config)`
   unconditionally and re-stepped all 576 intervals. Prewarming the batch alone would
   not have helped.
3. Nothing was computed until asked, so the 84s landed mid-demo.

Fixes: identity by `(scale, seed)`; replay frames cached on the run (as **domain
values**, not rendered JSON, so a cached frame still serialises into whichever language
the socket asked for); `_execute` replays *and* assembles in one pass so frames and
result come from the same stepping; prewarm both scales on startup as a background task.

**Correctness**: the prewarmed console is **byte-identical** to a plain `run_demo()` for
the same config. This mattered — the prewarm path assembles from collected diagnoses
rather than calling `run_demo`, so a divergence would have shown different numbers
depending on how the run happened to be produced.

The full run is ready **~85s after server start**. Restart the API before presenting.
`GET /api/runs` exposes `warm: true` per scale.

## 3. The alert-selection bug (full scale)

Symptoms: some alerts unclickable, some selected several cards at once, behaviour looked
random. It was fully deterministic.

**Root cause**: alerts were identified by `use_case`, which is **not unique**. A full run
has 24 fault panels across 5 use cases — 13 of them `uc1_network_node`. That single fact
produced every symptom: duplicate React keys (13 identical), `find(a => a.useCase ===
pinned)` always returning the *first* match, and an active-class test that matched all 13.

`console.py:117` already warned about exactly this ("matching on use_case would collide
once many faults share a category"); the frontend never got the memo.

**Fixed**: `Alert.id = "${index}:${entity}"`, unique per run, replacing `useCase` at all
**9** sites — App selection, AlertQueue key/active/click/aria, AnalystTab, MapTab
key/click, Transport.

### A second bug the same cause was hiding
`buildAlerts` joined stream onsets to panels **by use case**, so all 13 uc1 alerts
inherited the *first* uc1 fault's onset (e.g. an onset of 113 displayed as 80). That
drives the "forming" state, the formation progress bar and the lead-time gap on the
ribbon. Fault ids like `F-EX01-ACC` carry no entity, so the join was impossible
client-side — `FaultPanelOut.onset_interval` now carries ground truth per panel.
**24 distinct onsets for 24 panels.**

Tiny scale was never affected (3 panels, 3 distinct use cases), which is why this only
appeared on the full toggle.

## 4. Management view

Numbers were right; the table had the same class of defect:

- `<tr key={score.use_case}>` — 13 rows keyed `uc1_network_node`.
- The row→panel join was **by index**, correct only because all 24 specs happened to
  produce a panel. `console.py` appends a finding only when `_settled_report` returns
  non-`None`; one skip and every row below would show the **wrong element name** while
  the numbers stayed plausible.

**Fixed** by removing the join entirely: the table iterates `alerts` and reads
`alert.panel.score` (verified to be the *same object* as the scorecard row). Keys are
`alert.id`. Region added to each row, since 13 rows otherwise read identically.

Verified against the 24 alerts: 24/24 detected, mean lead 44.4 min, localization 100%,
false positives 0.0% (0 of 89 quiet intervals), decoys held 3/3, self-test PASS.
Verdicts by layer: access 14, home 6, core 2, content 2 — **totals 24**.

KPI tiles aggregate `scorecard.per_use_case`, not the panels — the right source, since it
covers every injected fault whether or not a panel was produced.

## 5. Layout and presentation

- **Ribbon legend** relabelled `decoy` → `benign transient` (the domain's own phrase).
  "Decoy" is harness vocabulary; on a rail where amber otherwise means "degrading" it
  read as a severity to act on. Colour kept orange at your request.
- **Ribbon marks are hoverable.** They always had `title` attributes, but the invisible
  scrubber (`.scrub`, `inset: 0`, `opacity: 0`) covered the whole ribbon and swallowed
  every hover. Fixed with `z-index` plus a ±4px hit-target pad. Tooltips were then
  replaced with a real tooltip that opens **upward**, because the bar is the last row of
  a `100vh` grid and native `title` opens downward off-screen.
- **Verdict header**: short headline (`headline_short`, derived from the message key so
  heading and sentence can never name different faults), full sentence removed (it is the
  receipt's Claim on the right), band pill shortened to `Critical`/`Crítico`, chips on one
  row flush with the heading, header height **fixed at 66px** so it cannot shift the view
  as verdicts land.
- **Verdict body** is now two columns that both run to the transport bar, each a flex
  column with exactly one growing card — so the bottoms align by construction. Beats moved
  into the left column as a *Detection narrative* card.
- **Graph enlarged**: the `viewBox` was 520×230 and **width-limited**, so a taller card
  only added letterboxing. Canvas is now 520×320 via a `vy()` scale helper applied to the
  authored coordinates (radii and font sizes deliberately untouched, so nodes stay round).
  In a 1130px column the drawing went from ~500px to ~695px tall.
- **Alert rail**: the rail no longer scrolls as a whole. `.rail-scroll` is the only
  scrolling region; the competence boundary and honest instruments are pinned below it and
  compacted (~90px reclaimed) so the alert list can grow.
- **Ribbon speed**: paced to a **target duration** rather than a fixed per-frame delay.
  Full was 576 × 220ms = 127s; now `TARGET_RUN_MS / totalIntervals`, clamped between 40ms
  and 220ms → **full is exactly 60s at 1×**, tiny unchanged at 13.2s. Speed buttons still
  divide (2× = 30s, 8× = 7.5s).

## Deliberately NOT done

**The Structural Health Index gauge.** The twin's `SHI 20 / 100` is a hand-authored
keyframe series (`si_core/ui/movistar_si_twin.html:428-437`), linearly interpolated — the
twin's own header says *"scripted replay"*. **The engine has never measured an SHI**;
`si_core` only has `health_band`, a string. Restoring the gauge would mean inventing a
number, which breaks this codebase's own rule (`format.ts`: *"display what the API
measured, and derive nothing that could be mistaken for a measurement"*).

If you want it for the video, the honest route is to **define SHI in `si_core`** as a real
0–100 index computed from what the engine already has — mean departure vs learned
baseline, affected fraction, persistence — so it becomes measured and scoreable. That
needs your sign-off on the formula. Left as is at your instruction.

## Process note worth keeping

Twice this session a CSS edit **silently did nothing** — the multi-line anchor I matched
on had been changed by an earlier edit, so the replace found nothing while the script
reported success and the build stayed green. Both were caught only by grepping the served
CSS for the new rule and finding the *old* one still there.

If you continue with an agent: **verify edits against the built artefact, not the build
exit code**, and make edit scripts assert their anchors exist rather than printing
success unconditionally.
